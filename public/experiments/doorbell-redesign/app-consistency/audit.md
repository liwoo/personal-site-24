# App-wide design consistency audit

Status: proposed for review · 26 October 2026 · source snapshot `bd5798ac05f9661d3d8bbf96615f6519d5a84a7e`.

The remaining page families are not yet consistent with the [Home direction](../home-page/audit.md). The main divergence is in shared control behavior, navigation semantics and state presentation, followed by task-specific hierarchy in checkout, courier forms and account settings. Fixing the shared components first will remove more inconsistency than separately restyling each screen.

[Review guide and visual boards](README.md) · [Shared design language](../design-language.md) · [Screen inventory](inventory.md) · [Visual concepts](index.html) · [Character and feedback](../brand-character/README.md)

## Scope and evidence

This is a source-based UX audit of the remaining page families, route/workflow entry points and selected shared widgets. All **112 Dart files under `lib/screens`** are inventoried, including Home/search files already covered in the original audit, supporting widgets and legacy code. The inventory is a coverage map, not a claim that 112 separate pages were interactively tested.

The follow-up does not use current-build emulator screenshots or exercise production transactions. **Confirmed** below means directly visible in source. **Validate** means a layout, accessibility or interaction risk requiring runtime testing. Proposed boards show representative layouts using sample data; they are not before/after captures, live payment interfaces or completed application changes. External hosted payment, support, account-deletion and policy pages are integration boundaries, not audited external websites.

Main route/workflow tracing is based on `main.dart`, `utils/navigation.dart`, `utils/shop.dart`, `utils/cart.dart`, authentication workflows and account links. The `/deprecated-account` name is misleading: it still points to the current Account/Settings experience and must not be dismissed as dead code. The older notification inbox is separately registered at `/home/notifications`; a visible navigation path to it was not established in this audit.

P0 = remove a blocking/ambiguous task pattern; P1 = shared language and major page alignment; P2 = secondary refinements or work dependent on product/data decisions. These priorities are judgments, not measured user-impact scores.

## Shopping and discovery

### Services, categories, collections, groceries and local-shop catalogues

**Confirmed:** service browsing has search and a morphing category strip; Groceries is a dedicated path selected by service name. Grocery cards format prices as `K…`, while product/cart surfaces use currency helpers. Grocery discovery adds deals, popular items, aisles and shops. Collections and categories share `ProductsPage`; retail catalogues already have scoped search and category lists. These are useful foundations, not missing features to rebuild.

**Change:** use the same title/search/labelled-category rhythm as Home. Lead with the requested service's task, then one discovery section at a time. Standardise product units, currency, merchant metadata and quick-buy controls. Keep stable labels when the category strip collapses. Show closed/unavailable text and distinguish a product result from a shop result. Preserve pagination, query and scroll position across detail navigation. Retain real favourites and quick-add behavior where supported.

**Validate:** the retail header puts type, category, rating and an age marker in one row; long names and large text need wrapping. The generic product card defaults a missing tag to “Popular”; do not display an implied ranking without evidence.

Evidence: [service dispatch](https://github.com/Tiyeni/doorbell-app/blob/bd5798ac05f9661d3d8bbf96615f6519d5a84a7e/apps/doorbell_app/lib/screens/services/service_screen.dart#L37), [grocery prices](https://github.com/Tiyeni/doorbell-app/blob/bd5798ac05f9661d3d8bbf96615f6519d5a84a7e/apps/doorbell_app/lib/screens/groceries/groceries_screen.dart#L844), [retail header](https://github.com/Tiyeni/doorbell-app/blob/bd5798ac05f9661d3d8bbf96615f6519d5a84a7e/apps/doorbell_app/lib/screens/ecommerce/ecommerce_screen.dart#L265), [catalogue search](https://github.com/Tiyeni/doorbell-app/blob/bd5798ac05f9661d3d8bbf96615f6519d5a84a7e/apps/doorbell_app/lib/screens/ecommerce/ecommerce_screen.dart#L383), [product fallback tag](https://github.com/Tiyeni/doorbell-app/blob/bd5798ac05f9661d3d8bbf96615f6519d5a84a7e/apps/doorbell_app/lib/widgets/products_page/product_card.dart#L112), [category/collection page](https://github.com/Tiyeni/doorbell-app/blob/bd5798ac05f9661d3d8bbf96615f6519d5a84a7e/apps/doorbell_app/lib/screens/categories/categories_screen.dart#L114). ### Product details and options

**Confirmed:** product details already provide choices, optional notes, a real favourite toggle, availability/closed states, and quantity plus price in a bottom action. Invalid choices trigger field marking and scrolling/shaking; preserve this validation. There is review-placeholder code in the file, but the rating toggle in the shown header is commented out, so this audit does **not** claim fabricated reviews are currently displayed.

**Change:** name, shop and price first; short description; labelled required/optional groups; notes last. Use full-row selections, clear min/max requirements, normal-price/surcharge hierarchy and one retro **Add to cart · MK …** action on a quiet footer. Keep the dynamic total and all product-specific rules. Visible text should explain required selections without relying on shaking or haptics. Keep unavailable/closed explanations in place of the purchase action.

**Validate:** footer space, keyboard behavior, long modifier names, accessible quantity targets and repeated submit handling. Keep the overlay favourite reachable and named without overlapping Back.

Evidence: [details/options](https://github.com/Tiyeni/doorbell-app/blob/bd5798ac05f9661d3d8bbf96615f6519d5a84a7e/apps/doorbell_app/lib/screens/food_more_details/food_more_details.dart#L475), [add action](https://github.com/Tiyeni/doorbell-app/blob/bd5798ac05f9661d3d8bbf96615f6519d5a84a7e/apps/doorbell_app/lib/screens/food_more_details/food_more_details.dart#L754), [choice rules](https://github.com/Tiyeni/doorbell-app/blob/bd5798ac05f9661d3d8bbf96615f6519d5a84a7e/apps/doorbell_app/lib/screens/food_more_details/widgets/choice_section.dart#L199), [commented rating toggle](https://github.com/Tiyeni/doorbell-app/blob/bd5798ac05f9661d3d8bbf96615f6519d5a84a7e/apps/doorbell_app/lib/screens/food_more_details/food_more_details.dart#L1113). ### Cart and favourites

**Confirmed:** Cart is opened by category/service, has expandable option details, a receipt-style total/footer, a repair utility and an empty-cart state. Favourites uses real saved products, swipe-to-remove, an explicit remove icon and quick buy. It should not be treated as a placeholder page.

**Change:** preserve service-cart selection. Inside each cart, use calm item rows with shop, selected variants, quantity, line price and explicit Remove; keep subtotal/fees separately labelled. Show the meaningful options summary without requiring every row to be expanded. Keep repair available in a secondary Help/More location rather than presenting technical repair as a normal shopping step. Empty cart gets **Browse shops**; favourites gets **Browse products** and an explanation. Review removal confirmation/undo against existing synchronization rather than adding optimistic undo without backend support.

**Validate:** clearing the last item, cart update failure, guest continuation, shop closure, unavailable items, quantity limits and multiple service carts. Do not hide the data needed to explain a changed total.

Evidence: [cart repair](https://github.com/Tiyeni/doorbell-app/blob/bd5798ac05f9661d3d8bbf96615f6519d5a84a7e/apps/doorbell_app/lib/screens/cart/cart_screen.dart#L224), [cart contents/footer](https://github.com/Tiyeni/doorbell-app/blob/bd5798ac05f9661d3d8bbf96615f6519d5a84a7e/apps/doorbell_app/lib/screens/cart/cart_screen.dart#L376), [item options](https://github.com/Tiyeni/doorbell-app/blob/bd5798ac05f9661d3d8bbf96615f6519d5a84a7e/apps/doorbell_app/lib/screens/cart/widgets/cart_item.dart#L116), [cart selection](https://github.com/Tiyeni/doorbell-app/blob/bd5798ac05f9661d3d8bbf96615f6519d5a84a7e/apps/doorbell_app/lib/utils/cart.dart#L14), [favourites](https://github.com/Tiyeni/doorbell-app/blob/bd5798ac05f9661d3d8bbf96615f6519d5a84a7e/apps/doorbell_app/lib/screens/faves/faves_screen.dart#L98). ## Checkout, payment and addresses

### Checkout review and confirmation

**Confirmed:** checkout includes delivery/pickup, address, delivery time, payment, notes, discount and a total before opening a second confirmation sheet. That sheet uses a 1.5-second press-and-hold action with repeated haptics; its nested Button has an empty normal-tap callback. The sheet is fixed to half the screen height.

**Change:** one clear review hierarchy: fulfilment/address → time → payment → optional notes/discount → total → **Place order · MK …**. Preserve an explicit final review if needed, but use a normal button with a clear irreversible-action label. If hold-to-confirm remains required, provide an equivalent accessible action. Confirmation must state whether this places the order, opens payment or confirms cash on delivery; do not label an unpaid order as paid.

**Validate:** large text/keyboard in the confirmation sheet, disabled explanations, cash eligibility, stale delivery-time/fee recalculation, closed shops, price changes and duplicate submission. This is a UX recommendation; no payment logic is changed.

Evidence: [checkout form](https://github.com/Tiyeni/doorbell-app/blob/bd5798ac05f9661d3d8bbf96615f6519d5a84a7e/apps/doorbell_app/lib/screens/checkout/checkout_screen.dart#L342), [hold duration](https://github.com/Tiyeni/doorbell-app/blob/bd5798ac05f9661d3d8bbf96615f6519d5a84a7e/apps/doorbell_app/lib/screens/checkout/checkout_screen.dart#L740), [confirmation gesture](https://github.com/Tiyeni/doorbell-app/blob/bd5798ac05f9661d3d8bbf96615f6519d5a84a7e/apps/doorbell_app/lib/screens/checkout/checkout_screen.dart#L850), [closed-shop guard](https://github.com/Tiyeni/doorbell-app/blob/bd5798ac05f9661d3d8bbf96615f6519d5a84a7e/apps/doorbell_app/lib/screens/checkout/checkout_screen.dart#L1043), [cash eligibility](https://github.com/Tiyeni/doorbell-app/blob/bd5798ac05f9661d3d8bbf96615f6519d5a84a7e/apps/doorbell_app/lib/screens/checkout/widgets/payment.dart#L209). Priority P0.

### Payment number, Airtel and hosted/OneKhusa payment

**Confirmed:** number selection already explains where the PIN prompt will appear and validates the provider. Airtel has **Confirm on your phone**, manual status checking and a terminal return action. OneKhusa separates genuine payment codes from hosted-page instructions, provides copy feedback, pending/terminal states, optional help and a leave confirmation. Preserve these distinctions.

**Change:** one task template with **Payment**, order reference, amount, provider and explicit current state. Keep provider branding subordinate to the shared typography and action hierarchy. One primary action reflects the current task: **Continue to secure payment**, **Check payment status**, or **View order**. Keep optional video/how-to content collapsed and support below the main task. Replace decorative monitoring glow with a stable status label and small progress indicator.

**Critical consistency rule:** network interruption or a polling timeout means **status not yet confirmed**, not “failed”. Do not invite a second payment before reconciling the existing order. Do not ask for a wallet PIN inside Doorbell. Existing back-to-order and resumable-payment behavior must survive any styling change.

### City, location, saved addresses and shared pins

**Confirmed:** location entry supports landmarks, current location, map positioning, city bounds and naming; saved-address management supports switching, editing/deleting and WhatsApp location import. Courier uses a separate address sheet with saved/recent choices and duplicate-location checks. These capabilities must remain.

**Change:** use one selection-row pattern and consistent **Use this address** confirmation. Keep the location label, landmark/address and city readable. Give **Use current location**, **Search for a place**, and **Add shared location** clear labels. In map mode, prioritise the pin and chosen location; keep guidance in one compact panel. Separate choosing an address from deleting it. An account-level Saved addresses entry is a proposed new entry point reusing this flow, not an existing Account feature.

**Validate:** denied permissions, no place results, map loading, city mismatch, pickup/drop-off equality, imported pins, long addresses and safe-area keyboard behavior. Do not silently switch a city or remove incompatible cart contents.

## Orders, delivery and errands

### Orders list, tracking, details, receipts and reorder

**Confirmed:** Orders has status tabs, paginated lists and a resumable payment link for applicable unpaid orders. Cards lead with total and product preview; status chips use many hard-coded colours. Tracking combines maps, status/estimate, rider contacts, warning/details panels and a prominently styled rating action. Receipt sharing and reorder already exist.

**Change:** lead each order with merchant/service, status and reference; then amount/date and its one next action. A proposed **Active / Past** grouping is an IA decision requiring a mapping from existing statuses, not a label-only replacement. Preserve distinctions such as awaiting payment, awaiting confirmation, ready for pickup, out for delivery, delivered and cancelled. Tracking should answer **What is happening? When? What can I do?** before secondary panels. Use a readable timeline and textual last-update/fallback state when a map is unavailable. Group rider contact and support without covering the map/action area. Keep receipt sharing secondary; show “Total paid” only when payment is confirmed, otherwise label the order total/payment due accurately.

**Validate:** unavailable rider/ETA/map, late status, pickup versus delivery, receipt generation failure, partial/unavailable reorder and an unpaid order returning from payment. Order details currently labels its amount **Total Paid** unconditionally in the inspected summary; verify the screen's reachable payment states before treating that as a reproduced customer error.

## Account, communications and supporting pages

### Account, profile editing, security, favourites and affiliates

**Confirmed:** Account already groups account/support/privacy rows, but support is spread across four sibling actions. Guest copy reads “Sign in to for more”. Security contains “Revoking your deprecated-account…” in customer-facing text and opens external change-phone/deletion pages. Affiliates already has status-labelled codes, counts and recovery/empty states.

**Change:** keep grouped rows and standardise titles, spacing, chevrons and text roles. Use **Personal details**, **Saved addresses** (new entry), **Favourites**, **Notification settings**, **Security**, then **Help & support**, **About Doorbell** and sign out. Keep Affiliates visible to eligible users; do not remove the function to declutter. Put merchant registration/social links in About as proposed on Home. ## Implementation order and acceptance

1. **Shared foundation:** button/input/title/status tokens, accessible back/close/quantity targets, busy-state activation guard, state panels and modal rules. Preserve existing data, submit guards and platform behavior.
2. **Complete a vertical journey:** service list → product options → service cart → checkout → payment → order status. Confirm both shopping and courier paths; the design language must survive real state transitions.
3. **Secondary surfaces:** account, notification settings, offers, ratings, announcements and onboarding. Decide legacy route ownership separately.

Before implementation is considered complete, verify each family in the inventory at 360/390/412 logical widths, large text through 200%, light/dark, keyboard visible/hidden and reduced motion. Run TalkBack/VoiceOver through focus, required options, loading, selection and error recovery. These are proposed acceptance checks, not tests already passed by the Flutter app.

| Journey | Required state checks |
|---|---|
| Browse and product | Loading, no matches, closed shop, unavailable variant, required-choice error, add in progress/error, return retains query |
| Cart and checkout | Empty, last-item removal, multiple service carts, update failure, guest gate, changed total/fee, no time slot, closed shop, large-text confirmation |
| Payment | Provider number error, genuine TAN versus hosted fallback, waiting, interruption/unknown, confirmed failure, success, leave/resume same order |
| Address and errands | Permission denied, city bounds, long address, shared pin, same pickup/drop-off, maximum errands, unavailable quote, preserved draft |
| Orders and account | Empty/history, unpaid resume, cancelled/late/fulfilled, missing rider/map, receipt error, favourite removal, guest/registered, permissions off/test error |
| Supporting screens | No offers, expired/not-qualified deal, rating submit error, announcement/terms loading failure, small-width warning, forced update, service disabled |

Review the shared language plus representative boards before agreeing implementation scope. The concepts illustrate information hierarchy, not production behavior; no assumption of real fees, delivery estimates, eligibility, payment success or customer data should be taken from them.
